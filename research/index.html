The seam between merge and production

Coding agents made it fast to write and merge a change. They did not make it any faster to find out what actually shipped. This note reports how existing deploy tools score a check that examined nothing, the read-back method seamkit uses instead, and what 29 rounds of adversarial review found while it was built.

azank azank1/seamkit Apache-2.0 0.1.0 on npm 0.2.0 in review

1The seam

A merge is a claim about the repository, and a successful deploy is a claim about a build. What production serves is the only thing a user ever meets. Between those points sit a build, an artifact, a host's deploy step and usually a cache or an edge network, and each of them can drop a change without any earlier signal turning red. A merge stays green when the deploy meant to carry it is cancelled. A deploy stays successful when it built an older commit. A rollback leaves every merged pull request looking finished.

None of this is new. What has changed is the traffic. When agents write and merge most of the code, the number of merges per day rises while the number of people watching each one reach production does not, and the gap between the two ends becomes the place where defects go unseen. This project calls that gap the seam.

2How existing tools score a check that examined nothing

The survey covered progressive-delivery controllers, deploy trackers, merge-flow policy tools and the release tools that appeared for agent-written code in 2025 and 2026. It was made from public documentation on 2026-10-14, and every claim in the full write-up carries a source. The question that separated the tools most clearly was what each does when a check looks at nothing: no metric values, no matching data, or a required check that never ran.

Three results stand out. A mature canary judge documents an all-empty group as a perfect score, which is exactly the failure seamkit exists to prevent. GitHub alone gives two opposite answers to the same absence of evidence, a permanent block in one configuration and a silent pass in another. And most tools trust the commit that CI says it deployed rather than asking production which commit it runs.

The most telling result was indirect. Many repositories in 2026 carry a hand-written check that compares a version endpoint with the expected commit, which suggests that reading production back is a recognised need without a packaged tool. Each element of seamkit has precedent somewhere; the combination of a separate examined-nothing outcome, a read-back of production by commit ancestry, and a surface that agents can call without Kubernetes or a hosted service was not found in any one tool.

3Method

seamkit reads production read-only and compares it with the repository's own history. Production names the commit it was built from in a small version document, which seamkit stamp writes at build time and which refuses to vouch for a build made from uncommitted changes. For every change merged into the default branch, readback asks whether the running commit contains it, by git ancestry. A change can also carry a card in its pull request description that names text the built output must contain, and readback then searches the served page and the scripts it loads for that text.

Runs are recorded on a branch of the repository itself. That ledger is what lets a later run tell a change that left production, which was seen live before and is absent now, from one that never arrived. No model runs inside the tool. The same inputs give the same verdicts, and seamkit replay re-runs every recorded run against its recorded inputs and checks that the verdicts match byte for byte.

live

Production's commit contains the change, and every marker its card names was found in what production serves.

not live

The change was seen live by an earlier run and is absent now, as after a rollback.

not proven

The change is absent and was never seen live, or its evidence could not be read.

nothing to prove

The change's card declares that nothing deployed changes, and says why.

$ npx seamkit audit --url https://your.app
NOT LIVE  1 of 3  (1 fail)
  commit:5da1b19d6870  feat: third page
                       production runs 704857be812c, which does not contain this change;
                       it was seen live at 2026-10-25T16:29:08.574Z (event 6b6aa311cb41)
LIVE  2 of 3  (2 pass)
  ...
FAIL  readback  origin/main
  proven live 2 of 3 changes
  not live 1: seen live earlier, absent now
exit 1

4What adversarial review found

The 0.2.0 GitHub Action, which reads production back after every deploy and posts the verdict as a check run, was built under a loop of adversarial review. Each round ran six reviewing agents with distinct lenses, such as how a deploy is scoped, how the wait for production behaves, security, whether the documentation is true, the ledger's lifecycle, and whether the tests prove what they claim; rounds 26 to 29 turned two of them to the version stamp and the packaged artifacts. Every finding was then given to two independent skeptics instructed to refute it, and a completeness critic closed the round by looking for what the lenses had not run. Each fix was afterwards broken on purpose in the compiled code to confirm that a test fails.

Read by class, the findings say more than the totals. Three classes account for most of the late rounds, and each carries a lesson that applies beyond this tool.

Credentials leaking through git's own error text

Thirteen rounds (11, 12, 14 and 20 to 29) found a way for a token in a git remote URL to reach a public check run, which GitHub does not mask. The routes were trace output, a curl verbosity variable that turns tracing on whatever its value (introduced by the fix for round 11), trace settings read from git config, and passwords holding an unencoded @, quote, slash or line break that ended the scrub early. The defence has two layers: tracing is removed from git's environment at the source, and whatever git still writes is scrubbed with a rule that errs toward removing too much. Round 24 found that the shapes combine: a user name or password holding both an unencoded @ and a line break escaped a rule that handled each alone. The scrub now repeats until no URL in the text is followed by an @, and git's refusal of a URL holding a line break, which prints the URL whole, is replaced by the reason. Rounds 25 and 26 found routes outside the URL that git prints: the host curl names after splitting a URL differently from git, a remote git reads as a local path and quotes whole, a proxy that git cuts short, and remotes written in git's transport form. Each was one more wording a pattern had to know, so a third layer was added that knows none: the credentials git can see, in its configuration and the proxy variables, are hidden wherever they appear in what it writes. Round 27 found that a credential helper is one more source: git quotes a line it could not use from a helper's output, and the shell echoes a failing helper whole, token included. Those lines are no longer shown, and what a helper holds is hidden like the rest. Rounds 28 and 29 found the same class again in the shapes a shell gives a helper's words when it traces them (quoted values, joined quotes, a printf argument), and a GIT_CONFIG variable that pointed the lookup at a different file from the one git read, so the helper is now split into words the way the shell splits it.

Precedence rules that trade a bug for its mirror

Rounds 16 to 19 kept finding the same sentence of the report wrong in opposite ways: the note that explains a commit production runs but the checkout lacks. Each fix was a precedence rule over the outcomes of branch fetches, and each rule had a counter-case. The oscillation stopped in round 19, when the rules were replaced by a model of the order of events, the log of fetches made since production first reported the commit. Round 20 fixed the one remaining fallback in that model.

Names that git resolves before commits

git looks a name up as a ref before it treats it as an abbreviated commit id, so a tag or branch named like a short commit id moved a passing verdict onto a different commit. Rounds 13 to 17 closed the variants: a tag, a branch, both at once, an annotated tag's own id, and every ref namespace git tries. Round 23 added the converse test, that a ref of that name pointing at the deployed commit itself shadows nothing.

From round 11 on, 165 fixes were broken on purpose across 19 rounds by editing the compiled code and rerunning the tests. Every break is caught by the current tests. One more, in round 28, changed nothing, because the git in use already does what that fix does, so it is not counted. Several survived at first, and each of those exposed a missing test that was then written, which is the main reason for doing it.

5A first run on localhost

To check that the tool works for someone who has never seen it, a throwaway repository was served from localhost with python3 -m http.server and audited with the published 0.1.0 and with the packed 0.2.0 candidate. Both versions gave the same outcome at every step.

6What it does not prove

Readback proves that what production serves contains a change. It does not prove that the change behaves correctly, which remains the job of tests and monitoring. It cannot examine a database change, for which there is no adapter yet, so such a marker is reported as not examined rather than guessed. It needs to reach production over HTTP, and it trusts the version document the build stamped. A build made from uncommitted changes is stamped dirty and never counts as proof, but a build with no git history, such as an upload from the Vercel CLI, takes its commit from the host and cannot tell whether the files it was given were committed.

The 0.2.0 Action has run on GitHub-hosted runners against real Vercel deployments of a sample site. It passed the deploys that went live, failed a rollback as not live, and failed a deploy that Vercel built and GitHub listed as a successful production deployment while the rollback kept the address on the old build. Vercel is the only host it has met, it has run on Linux runners only, and Windows and macOS runners are untested.

7Next

seamkit today observes the two ends of the seam. The next step is to record evidence at the stages in between, the build's stamp, the host's deploy event and what the edge serves, so that a change reported as not live also says at which stage it was lost. That turns a verdict into the first answer of a debugging session.

After that, in order, come an MCP server so that a coding agent can ask whether its change shipped without a human running the command, carry, which lists the merged changes a deploy will ship before it runs, and a gate that evaluates each open pull request the way the deploy step will. The plan and its done-when conditions are in docs/architecture.md.
