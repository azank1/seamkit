Deterministic production checks

Merged is not shipped. Read production back.

seamkit asks production which commit it runs, compares that with your git history, and tells you which merged changes are actually live. It answers with an exit code that an agent, a CI step and a person all read the same way. No model runs inside it.

Outcomes

Four outcomes, one exit code each

Every check returns one of four outcomes. The exit code says which, so a script or an agent chaining commands with && can never proceed on a result it misread. Every non-zero code means "not a pass".

0pass

Something was examined, and everything held.

1fail

A change is not live or not proven.

3examined nothing

seamkit could not look, so it claims nothing.

4unclassified

No rule covers the case. It stops for a human.

2usage error

Bad arguments or configuration. No verdict was produced.

Only a pass is ever shown in green. Every count carries its denominator, as in "proven live 10 of 21 merged changes", and every verdict lists what it did not examine, with a reason. A check over zero items is examined nothing, never a pass.

Architecture

A pure judge, a thin shell, read-only adapters

seamkit follows the functional-core, imperative-shell pattern. Adapters observe the world, the core judges the observations, and the shell records both. Because a verdict is a pure function of recorded inputs, any past verdict can be recomputed from the ledger with seamkit replay, and one that comes out differently is a defect.

The npm package bundles all of this into one file, with yaml's licence in its notices. HTTP reads are bounded: 10 seconds and 5 MiB per response, 64 KiB for a version document, and 100 files or 25 MiB for a whole crawl of a site's bundle.

Readback

What happens in one readback

  1. Walk the historygit adapter

    Take the first-parent history of the default branch: one change per merged pull request or direct commit, the last 20 by default.

  2. Ask production which commit it runsversion adapter

    Read a version document from /version.json, /api/version or /version. A dirty build, a commit the repository lacks, or a web page served in its place is unreadable, never trusted.

  3. Search the served buildbundle adapter

    For changes whose scope card names markers, read the page and the same-origin scripts, styles and chunks it loads, and look for each marker's text. The adapter records what it read, never content.

  4. Judgecore

    A change is contained when its commit is an ancestor of the running commit (git merge-base --is-ancestor). Markers are present, absent, contradicted or unreadable, decided from the recorded observation.

  5. Compare with earlier runsledger

    A marker that a recorded run saw and that is missing now makes the change not live, as after a rollback, rather than merely not proven.

  6. Answer and recordshell

    Print verdicts grouped with problems first, exit with the outcome, and record the run as an event that seamkit replay can recompute.

Readback states

StateWhenOutcome
liveevery marker is presentpass

not_provena marker is absent and was never seen, or production's version contradicts itfail
not_provennothing is absent, but some marker could not be readexamined nothing
nothing_to_provethe change's card declares that nothing deployed changesexamined nothing

A change with nothing to prove is never reported as live. That claim is the author's, and accepting it is a human's call.

Use it

Six ways in, from one minute to a full ledger

Any developer · 1 minute

Audit a site you already run

From your repository, with no configuration. It takes the last 20 merged changes and gives advice for every gap it finds, so "examined nothing" becomes a list of next steps.

cd your-repo
npx seamkit audit --url https://your.app
Build engineer

Make production say what it runs

Write a version document at build time, or answer /api/version from a server function with the commit your host provides, such as VERCEL_GIT_COMMIT_SHA.

# before the build; bundlers copy public/ into the output
npx seamkit stamp --out public/version.json --require-clean
{ "schema": "seamkit.version/1", "commit": "<full commit id>",
  "dirty": false, "source": "git", "ref": "main" }
CI · GitHub Actions

Fail the pipeline when a change is not live

Run readback as a step once the deploy is live. It needs the full history, because containment is decided by commit ancestry. A packaged Action is next on the roadmap.

- uses: actions/checkout@v7
  with: { fetch-depth: 0 }
- uses: actions/setup-node@v7
  with: { node-version: 22 }
- run: npx --yes seamkit@0.1 readback --url https://your.app --last 20
Coding agents · Claude Code, Cursor, Codex

Give the agent one rule

The exit code is the contract, so one instruction in AGENTS.md or CLAUDE.md stops an agent calling a change done because it merged.

After a deploy, run
`npx seamkit readback --url https://your.app --pr <number> --json`.
The change is shipped only when it exits 0. Exit 1 means it is not
live or not proven, and exit 3 means production could not be examined.
Report the reasons; never call a change done on any other exit code.
Pull request authors

Prove more than the version with a scope card

A fenced block in the pull request description names text the built output must contain. It reaches the history only when the repository's merge message is "Pull request title and description".

```seamkit-card
card: 1
intent: Show a saved indicator after a note is synced.
layers: [frontend]
targets: [web]
markers:
  - kind: bundle
    text: "data-sync-state"
releaseNote: Notes now show when they were last saved.
```

The parser is strict and reports every problem in one pass, each naming the field and the fix. A marker must be text in the built output: a component name or a comment exists only in source and is never found.

Teams · rollbacks and audits

Keep a ledger in the repository

With a ledger, a later run can say a change was live and has left production. Events are content-addressed, and every recorded verdict can be recomputed byte for byte.

npx seamkit state init      # create the seamkit/state branch
npx seamkit readback --url https://your.app
npx seamkit state verify    # every file matches its name
npx seamkit replay          # recompute every recorded verdict
npx seamkit state sync      # merge and push, never forced

What seamkit touches

Production, read-only

HTTP GET only, bounded in time and size, never with credentials. URLs that carry credentials or a query string are refused, because URLs are recorded.

Your repository, one branch

It reads your history and writes only seamkit/state, with git plumbing that never touches your working tree, index or HEAD.

No model, no content

No model runs inside it. The ledger holds URLs, commit ids, marker texts and digests, never what production served.
