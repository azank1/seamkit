Engineer's guide

Put a readback after every deploy.

seamkit is a command that proves each merged change is live in production. It reads your git history, asks production which commit it runs, and exits 0 only when the change is there. This guide wires it into the three places that ship code: your terminal, your coding agent, and your CI.

You need

  • A git repository with your app, and Node 20 or later.
  • A production URL you can reach with a plain GET.
  • One build change so production can name its commit (step 2).
First audit: one command · Full setup: about 30 minutes

    Understand

    The shipping loop, and the step it closes

    Most pipelines stop at "deployed". seamkit adds the last step: read production back, compare it with the history, and hand a verdict to whoever shipped the change, whether that was a person, an agent or a CI job.

    Understand

    Inside one run

    Adapters read the world and report what they saw. A pure core judges those observations with no network, no clock and no model. The shell prints the verdicts, exits with the outcome and records the run. Because the judge is pure, seamkit replay can recompute every recorded verdict from the ledger.

    Understand

    Exit codes are the interface

    Every automation in this guide branches on these five codes and nothing else. Every non-zero code means "not a pass", so && chains stop safely.

    0pass

    Examined, and every change is live.

    1fail

    A change is not live, or not proven. Retry while a deploy rolls out; alert after.

    3examined nothing

    seamkit could not look. Fix what it could not read; the output says what.

    4unclassified

    No rule covers it. Stop for a human. Never retry.

    2usage

    Bad arguments or configuration. No verdict. Printed to stderr.

    1

    Install and run your first audit

    works todayterminal

    Run it from the repository that production is built from. audit needs no configuration: it checks the last 20 changes on your default branch, then prints advice for every gap it found.

    Try it once
    cd your-repo
npx seamkit audit --url https://your.app
    Pin it in the project
    npm install --save-dev --save-exact seamkit@0.1.0
npx seamkit version   # 0.1.0

    The first audit of most sites exits 3, "examined nothing", because production does not yet say which commit it runs. That is the expected start. Step 2 fixes it.

    2

    Make production name its commit

    works todaybuild

    Readback needs one fact from production: the full commit id it was built from. Pick the option that matches how you build. seamkit looks for /version.json, then /api/version, then /version.

    Static or bundled sites
    package.json
    {
  "scripts": {
    "prebuild": "seamkit stamp --out public/version.json",
    "build": "vite build"
  }
}

    Stamp prefers git. Where the build has no history, it uses the commit your CI or host provides (VERCEL_GIT_COMMIT_SHA, GITHUB_SHA, CF_PAGES_COMMIT_SHA, COMMIT_REF and others) and records which one.

    Apps with a server route
    app/api/version/route.tsNext.js on Vercel
    export function GET() {
  return Response.json(
    { commit: process.env.VERCEL_GIT_COMMIT_SHA },
    { headers: { 'cache-control': 'no-store' } },
  );
}

    Any server can answer {"commit": "<40 hex>"}. seamkit also reads fields named sha or git.commit.id that other tools serve.

    check it
    curl -s https://your.app/version.json
{ "schema": "seamkit.version/1", "commit": "492378ccca806fd3c85ea55dfaf69bdb7ff16838", "dirty": false, "source": "git", "ref": "main" }
npx seamkit audit --url https://your.app      # now proves changes by version

    A build stamped from a working tree with uncommitted changes is reported as unreadable, never trusted. Use seamkit stamp --require-clean in CI to refuse such builds outright.

    3

    Start the ledger

    works todayrepository

    Without history, seamkit can only say a change is not proven. With a ledger, it can say a change was live and has left production, which is what a rollback looks like. The ledger is a branch in your own repository, written with git plumbing that never touches your working tree, index or HEAD.

    npx seamkit state init       # create the seamkit/state branch
npx seamkit audit --url https://your.app   # recorded as an event from now on
npx seamkit state sync       # share it: merge with the remote branch and push, never forced
npx seamkit state verify     # every event file matches its SHA-256 name
npx seamkit replay           # recompute every recorded verdict; fails if any differs
    4

    Prove more than the version with scope cards

    works todaypull requestsoptional

    The version proves a change's commit is deployed. A card proves the change does what it claims in the build: it names text that production's served files must contain, or a separate version document, such as a server function's. Agents can write cards, because a card is a fenced block in the pull request description.

    pull request description
    ```seamkit-card
card: 1
intent: Show a saved indicator after a note is synced.
layers: [frontend]
targets: [web]
markers:
  - kind: bundle
    text: "data-sync-state"
releaseNote: Notes now show when they were last saved.
```

    One repository setting is required. Readback reads cards from merge commits, and GitHub copies the description into the merge commit only when the default commit message is Pull request title and description. Set it under Settings, General, Pull Requests, for merge commits and squash merges.

    A marker must be text in the built output. A component name or a comment exists only in source and will never be found; readback says so when the version shows the change is deployed.

    Automate

    Where to trigger it, and what to do with the answer

    One command, four places to call it. Each trigger runs the same readback and branches on the same exit codes, so a verdict means the same thing in your terminal, in an agent's session and in CI.

    5

    Your terminal: deploy, then wait for live

    works todaybashmake

    This script is the building block for every trigger below. It retries readback of the newest change on the default branch until production shows it or the deadline passes, and keeps polling runs out of the ledger.

    scripts/wait-live.sh
    #!/usr/bin/env bash
# Wait until production runs the newest change on the default branch.
# usage: scripts/wait-live.sh https://your.app [seconds]
url="$1"; deadline=$(( $(date +%s) + ${2:-300} ))
git fetch --quiet origin
while :; do
  npx seamkit readback --url "$url" --last 1 --no-record
  code=$?
  case $code in
    0) npx seamkit readback --url "$url" --last 1 >/dev/null; exit 0 ;;  # live: record it once
    2|4) exit $code ;;                                                # waiting will not help
  esac
  [ "$(date +%s)" -ge "$deadline" ] && exit $code
  sleep 15
done
    Makefile
    DEPLOY ?= vercel deploy --prod       # or your own deploy command
URL    ?= https://your.app

ship:
	$(DEPLOY)
	./scripts/wait-live.sh $(URL) 300

    Now make ship fails unless production actually runs the change, and the failure prints which change and why.

    6

    Coding agents: no "shipped" without exit 0

    works todayClaude CodeCodexCursor

    Agents report work as done when the pull request merges. Two layers stop that: an instruction every agent reads, and, in Claude Code, a hook that checks every deploy command the agent runs.

    AGENTS.md or CLAUDE.md
    ## Shipping
After a deploy, run `npx seamkit readback --url https://your.app --pr <number> --json`.
The change is shipped only when it exits 0. Exit 1 means it is not live or not proven, and
exit 3 means production could not be examined. Report the reasons; never call a change done
on any other exit code.
    .claude/settings.json
    {
  "hooks": {
    "PostToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/scripts/after-deploy.sh"
      }]
    }]
  }
}
    scripts/after-deploy.sh
    #!/usr/bin/env bash
# Runs after each shell command; acts only on deploys.
cmd=$(jq -r '.tool_input.command // ""')
case "$cmd" in
  *"vercel deploy"*|*"npm run deploy"*) ;;
  *) exit 0 ;;
esac
cd "$CLAUDE_PROJECT_DIR"
if ! out=$(./scripts/wait-live.sh https://your.app 300 2>&1); then
  echo "seamkit: the deploy is not proven live." >&2
  echo "$out" | tail -n 20 >&2
  exit 2   # stderr is shown to Claude
fi

    The hook uses jq to read the command Claude ran from the hook's JSON input. Match the patterns to your own deploy commands. A packaged hook set for Claude Code, Cursor and Codex is on the roadmap.

    7

    Local models and your own DevOps tools

    works todayany language--json

    A local model, an internal bot or a deploy script does not need an SDK. Run the command, read the exit code, and give the model the reasons. Expose it as a tool like this, and the model can check its own deploys without being able to fake the result.

    seamkit_tool.py
    import json, subprocess

def readback(url: str, pr: int | None = None) -> dict:
    """Is the change live in production? Give the model this tool's result as is."""
    args = ["npx", "seamkit", "readback", "--url", url, "--json"]
    if pr is not None:
        args += ["--pr", str(pr)]
    p = subprocess.run(args, capture_output=True, text=True)
    if p.returncode == 2:                       # usage error: text on stderr, no verdict
        return {"exit": 2, "error": p.stderr.strip()}
    doc = json.loads(p.stdout)
    return {
        "exit": p.returncode,                   # 0 shipped; anything else is not
        "outcome": doc["outcome"],
        "reasons": [r for v in doc["verdicts"] for r in v["reasons"]],
    }

    The same pattern works in Go, Rust or a shell pipeline. The exit code is the decision; the JSON is the explanation. An MCP server that offers these checks as tools to any MCP client is next, in M4.

    8

    CI: verify every production deploy, and watch for rollbacks

    seamkit Action · 0.2.0GitHub Actionscheck runs

    Two workflows cover CI. The first runs when your host reports a successful production deployment to GitHub, as Vercel does for connected repositories, and posts the verdict as a check run on the deployed commit. The second runs on a schedule, so a rollback or a hand deploy is caught even when nobody deployed through CI. Both keep the ledger, so "not live" means the change really left production.

    .github/workflows/readback.yml
    name: readback
on: deployment_status
permissions:
  contents: write   # to push seamkit/state
  checks: write     # to post the check run
jobs:
  readback:
    if: >-
      github.event.deployment_status.state == 'success' &&
      github.event.deployment.environment == 'Production'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }
      - uses: azank1/seamkit@v0.2.0
        with:
          url: https://your.app
          ledger: 'true'
    .github/workflows/watch.yml
    name: production watch
on:
  schedule: [{ cron: '*/30 * * * *' }]
  workflow_dispatch:
permissions:
  contents: write
  checks: write
jobs:
  watch:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }
      - uses: azank1/seamkit@v0.2.0
        with:
          url: https://your.app
          wait: '0'   # nothing is deploying

    The Action pulls the ledger, reads production back until it passes or wait runs out (60 seconds by default, recording nothing while it waits), records the run that counts, and pushes the ledger again, merging rather than forcing. Only a pass posts a success: not live and not proven fail the check, production that cannot be read fails it as examined nothing, and unclassified asks for a human. The step exits with seamkit's own code, and its outcome, exit-code and title outputs let later steps react. Without checks: write the verdict still stands and the step says which permission is missing.

    When you deploy from a workflow of your own, trigger on workflow_run of that workflow instead; the check run then goes on the commit it deployed, and a deploy that failed is skipped.

    Other CI systems run the CLI: Node 20 or later, the full history (no shallow clone), and push access to the seamkit/state branch if you keep the ledger there. Run npx --yes seamkit@0.2 state sync, then npx --yes seamkit@0.2 readback --url https://your.app --last 20, then state sync again whatever the result. Pass --branch when the default branch is not checked out as origin/HEAD.

    Troubleshooting

    seamkit audit prints advice for each of these. This table is the same advice in one place.

    You seeCauseFix
    Exit 3 for every changeProduction serves no version document, or serves a web page in its place.Step 2. Check with curl that the URL returns JSON with a full commit id.
    "commit unknown to this repository"The local clone has not fetched the deployed commit, or it was deployed from a branch that never merged.git fetch origin. If it persists, someone deployed by hand.
    "shallow clone"CI checked out a single commit.fetch-depth: 0, or git fetch --unshallow.
    Version unreadable, dirty buildThe build was stamped from uncommitted changes.Build from a clean tree; add --require-clean.
    Marker absent although the version contains the changeThe marker text is in source but not in the built output.Use text the bundle really ships, such as an attribute value or a user-facing string.
    "No change carries a seamkit-card"The merge setting drops pull request descriptions.Step 4: "Pull request title and description".
    Exit 2: URL refusedThe URL carries a query string or credentials, and URLs are recorded.Use a plain URL. Readback only needs public GETs.
    "cannot tell not live from not proven"There is no ledger yet.Step 3: seamkit state init.

    Commands in 0.1.0

    CommandDoes
    seamkit audit --url UReadback over the last 20 changes, with advice for every gap. --last N, --branch R, --json.
    seamkit readback --url UProve each change, or one with --pr N or --commit C. --last N, --branch R, --version-url V, --record or --no-record, --json.
    seamkit stampWrite the version document: --out F, --commit C, --require-clean.
    seamkit state init | list | verify | syncCreate, list, verify and share the ledger branch. sync --remote R.
    seamkit replay [event]Recompute recorded verdicts; fails if any comes out differently.
    seamkit check NAME · seamkit checksRun one registered check on a recorded input; list the checks.

    The production URL can also come from SEAMKIT_URL. seamkit sends only GETs to production, writes only the seamkit/state branch, records URLs, commit ids and digests but never content, and runs no model.
